# Supply chain

Nightjar runs inside an incident. That makes the artifact you deploy part of the
trust boundary: an image that was rebuilt by someone else, or a wheel that does not
correspond to the tagged commit, is a compromise that the case file cannot detect.
This page says what is published, what is signed, and how to check it before the
first incident.

## Artifacts

| Artifact | Name | Built by |
| --- | --- | --- |
| Python distribution | `nightjar-ir` | `.github/workflows/release.yml` |
| API / worker / lab image | `ghcr.io/crastatelvin/nightjar` | `.github/workflows/images.yml` |
| Web image | `ghcr.io/crastatelvin/nightjar-web` | `.github/workflows/images.yml` |

Both images are built for `linux/amd64` and `linux/arm64`. The wheel and the images
come from the same tagged commit; `nightjarctl --version` reports the version both
were built from.

## What is signed

Images are signed with [cosign](https://docs.sigstore.dev/cosign/overview/) in
keyless mode. There is no long-lived signing key in the repository or in CI: the
workflow exchanges the job's GitHub OIDC token for a short-lived certificate, and the
signature is recorded in the public Rekor transparency log. Verification therefore
checks *who built it and from which workflow*, not *which secret signed it*.

The signature covers the image **digest**, not the tag. A tag can be moved; a digest
cannot. Pin the digest in production.

Each image also carries OCI attestations generated by BuildKit:

- **SBOM** (`sbom: true`) — the package inventory inside the image.
- **Provenance** (`provenance: mode=max`) — the source repository, commit, Dockerfile,
  build arguments, and builder. Max mode records the build steps, not just the final
  reference.

Neither attestation is fetched from a mutable URL; both are attached to the image
manifest and returned by the registry.

## Verify an image

```bash
IMAGE=ghcr.io/crastatelvin/nightjar
DIGEST=sha256:...   # from the release notes or `docker buildx imagetools inspect`

cosign verify "${IMAGE}@${DIGEST}" \
  --certificate-identity-regexp '^https://github.com/crastatelvin/nightjar/.github/workflows/images.yml@.*$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

A successful verification prints the certificate identity and the Rekor entry. If the
identity does not match the workflow above, stop: the image was signed by something
else.

Inspect what is inside:

```bash
docker buildx imagetools inspect "${IMAGE}@${DIGEST}" --format '{{json .SBOM}}'
docker buildx imagetools inspect "${IMAGE}@${DIGEST}" --format '{{json .Provenance}}'
```

The attestations are BuildKit's OCI attestations, not separate Sigstore
attestations, so they are read from the manifest rather than with `cosign
verify-attestation`. If your registry UI hides them, `docker buildx imagetools
inspect` is the reliable view.

## Verify the wheel

The release workflow installs the wheel into an empty environment and starts the CLI
before publishing, so a wheel that cannot start never reaches PyPI.

```bash
pip download --no-deps --dest /tmp/nightjar nightjar-ir==0.1.0
sha256sum /tmp/nightjar/*
# Compare the hash with https://pypi.org/pypi/nightjar-ir/0.1.0/json (digests.sha256)
pip install /tmp/nightjar/nightjar_ir-0.1.0-py3-none-any.whl
```

Pin the version in a requirements file, and use `--require-hashes` where the
environment can maintain one. A hash pin is the wheel's equivalent of a digest pin.

## Deploy by digest

```yaml
services:
  api:
    image: ghcr.io/crastatelvin/nightjar@sha256:...
```

A digest pin makes an unexpected rebuild visible: `docker compose up` pulls the same
bytes or fails, rather than silently running a new `latest`. Update the digest as
part of a release, review the diff, and keep the previous digest recorded in the
case file of the change that deployed it.

## Static analysis

`.github/workflows/codeql.yml` runs CodeQL with the `security-extended` query pack over
the Python package and the Next.js app on every push to `main`, every pull request,
and a weekly schedule. `security-extended` is the pack that is still precise enough to
gate a merge; `security-and-quality` is noisy enough that a small team stops reading
it.

Publishing SARIF requires either a public repository or GitHub Advanced Security on a
private one. Nightjar is private until 0.1, so the job skips rather than failing on a
permission error while that is true; on a public repository it gates automatically.
To turn it on earlier, enable code scanning in the repository settings and set the
`NIGHTJAR_CODE_SCANNING` repository variable to `true`. Until then, `ruff`, `mypy`,
and the test suite are the checks that run on every change.

## Runtime lines

The container images run the same Python and Node versions the repository tests:
Python 3.14, as pinned in `PYTHON_VERSION`, `requires-python`, and the release job;
Node 24, as used by the local toolchain in `.tools/`. A base-image major bump is
therefore not a dependency update - it changes the interpreter and the standard
library the product actually runs on, and has to move `pyproject.toml`, the CI
matrix, the release job, and the local toolchain in one change. Dependabot is
configured to ignore base-image majors and to keep sending patch and minor updates,
which is where the fixes are.

## Limits

- Signing proves origin, not safety. A signed image can still contain a vulnerable
  dependency; the SBOM and the security checklist are how you answer that question.
- Keyless verification needs network access to Rekor and the OIDC issuer the first
  time; offline verification requires saving the certificate chain and the bundle.
- Container scanning and dependency alerts are configured in the repository
  (`.github/dependabot.yml`); a finding still has to be triaged by a person.
- The host that runs Nightjar is outside these guarantees. Harden it per
  [docs/security/checklist.md](security/checklist.md).
